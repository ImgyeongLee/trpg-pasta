# 헌법 (Constitution)

모든 스펙·계획·코드가 따라야 하는 원칙. 기능 스펙보다 우선한다.
바꾸려면 사용자의 명시적인 동의가 필요하고, 바꾼 내용은 맨 아래 "개정 기록"에 남긴다.

## 1. 누구를 위한 앱인가

**TRPG를 CCFOLIA·Roll20 같은 온라인 세션으로 진행하는 GM**의 데스크탑 도구 모음이다.
시나리오를 미리 정리해 두고(준비), 세션 중에는 눌러서 바로 복사해 채팅에 붙여넣는다(진행).

- 판단 기준은 **세션 중에 GM이 얼마나 빨리, 실수 없이 붙여넣을 수 있는가**다.
- 자동 처리는 초안일 뿐이고 **사람이 마지막에 고친다.** 자동 처리가 틀릴 수 있다는 전제로, 고치기 쉽게 만든다.
- 사람에게 「확인했음」 표시를 강요하지 않는다. 정리가 덜 됐어도 **복사는 언제나 가능**하다.

## 2. 화면 (UI) 규칙

- **이모지 금지.** 아이콘은 Lucide만 쓴다. Svelte에서는 `src/lib/icons.ts` 묶음에서 가져오고(개별 경로 import), 편집기(CodeMirror) 안에서는 `src/lib/scenario/editor/icons.ts`의 SVG 문자열을 쓴다.
- **포인트 색은 초록.** `--accent`, `--accent-soft`, `--accent-contrast` 토큰을 쓴다. 보라색 포인트 금지, 색 hex를 컴포넌트에 직접 쓰지 않는다. (예외: 사용자가 고르는 태그 색 — `--tag` 변수로 넘긴다)
- **기본(native) 컨트롤 대신 앱 자체 컴포넌트.** 고르기는 `Select`, 켜고 끄기는 `Switch`, 지우기는 `ConfirmButton`(두 번 누르기), 태그는 `TagPicker`. `<select>`·체크박스를 새로 쓰지 않는다.
- **지우기는 되돌릴 수 있거나 두 번 눌러야 한다.** 한 번 클릭으로 사라지는 파괴적 동작은 만들지 않는다.
- **라이트/다크 모드 모두** 가독성이 좋아야 한다. 색은 `src/app.css`의 토큰을 쓰고, 두 테마에서 화면을 본다.
- **지금 어디를 고치고 있는지 항상 보여야 한다.** (커서·현재 줄·선택 상태)
- 글꼴은 **Pretendard 고정** (앱에 넣은 가변 글꼴, 유니코드 범위별 조각만 읽기).
- 화면 문구는 **한국어**. 짧고, 버튼은 동사로 끝낸다 (「그룹으로 묶기」, 「줄로 풀기」).

## 3. 성능

- 앱의 성능을 떨어뜨리는 변경은 하지 않는다. 새 기능·의존성은 시작 시간, 집합 전환, 입력 지연을 늘리지 않는지 확인한다.
- 집합(섹션) 전환은 수십 ms 안. 그래서 집합은 **100~250줄**로 나눈다.
- 긴 PDF는 **조각(청크)으로** 처리해 첫 집합을 빨리 보여준다. 기다리는 동안 앱이 멈추지 않는다.
- 문장 분리·조사 교정처럼 무거운 글 처리는 **Rust**에서 한다.
- 큰 데이터(원본 PDF 바이트 등)는 깊은 반응형(`$state`)으로 만들지 않는다 (`$state.raw`).

## 4. 데이터와 개인정보

- **자동 저장하지 않는다.** 저장은 사용자가 한다 (「저장」 버튼·⌘S). 저장 안 된 채로 닫거나 새로 시작하면 경고한다.
- **세이브는 가볍게.** 원본 PDF·그림은 넣지 않고 위치·지문만 기록한다. gzip JSON(`.trpgsave`).
- **예전 세이브는 계속 열려야 한다.** 형식이 바뀌면 읽을 때 새 형식으로 바꾼다 (예: GM 정보 줄 → GM 정보 그룹).
- **오프라인이 기본.** 네트워크는 사용자가 요청한 구글 문서 가져오기에만 쓴다 (공개 링크, 로그인 없음). 글꼴·라이브러리는 앱에 넣는다.
- 사용자 파일 경로는 **Rust의 대화상자**로만 고르고 쓴다. 프론트엔드가 임의 경로에 쓰지 않는다.
- 외부 서비스로 개인정보를 보내지 않는다.

## 5. 라이선스와 의존성

- 앱 라이선스는 **AGPL-3.0-only**. 넣는 의존성·글꼴·에셋은 이와 함께 쓸 수 있어야 한다 (예: Pretendard는 SIL OFL 1.1).
- 의존성은 **버전을 고정**하고, 추가할 때 이유를 plan에 적는다.

## 6. 개발 방식

- **스펙 주도 개발**: [README.md](README.md)의 흐름(명세 → 사용자 확인 → 계획 → 작업 → 구현 → 검증 → 스펙 갱신)을 따른다.
- 사용자가 결정한 것은 스펙의 「결정 기록」에 남겨 다시 뒤집지 않는다. 뒤집으려면 사용자에게 묻는다.
- 코드는 주변 코드처럼 쓴다: 주석은 한국어, 왜 그렇게 했는지를 짧게.
- 검증 없이 「됐다」고 하지 않는다: `npm run check`, Rust를 건드리면 `cargo test`·`cargo clippy`, 화면은 실제로 띄워 확인한다.
- 커밋·푸시는 사용자가 요청할 때만 한다.
